Bloque 1 · El flujo

El ciclo de vida de una funcionalidad

1. La tarea

Nace en un tablero (Jira, Trello) con un qué y un para qué. Ustedes estiman cuánto toma; al principio se van a equivocar, y es normal.

2. La rama y el PR

Nadie toca main directo. Se trabaja en una rama y se abre un pull request con descripción clara y capturas.

3. El code review

Otra persona lee su código antes de que entre y pide cambios. No es personal: es la herramienta de calidad más barata que existe.

4. QA

Alguien intenta romper lo que hicieron: teléfono viejo, sin internet, girando la pantalla. Si no lo rompen ellos, lo rompe el usuario.

5. El release

Build firmado, versión numerada, notas de versión, lanzamiento por fases. Después, monitoreo de errores en producción.

6. El mantenimiento

La mayor parte de la vida de una app no es construirla: es mantenerla. Por eso importa escribir código que otro pueda leer.

El café de hace un momento es la tarea del punto 1: nunca llega completa. Preguntar lo que falta antes de programar es parte del trabajo.
Bloque 1 · La práctica

Lo que les van a pedir, y lo que nadie les dice

Lo que dice el papel
  • Integrarse a un equipo con una app ya en producción.
  • Implementar componentes de UI y consumir APIs internas.
  • Participar en code reviews: recibir y dar retroalimentación.
  • Usar Git y un tablero de tareas como parte del flujo diario.
  • Ayudar a encontrar y corregir errores en producción.
Lo que nadie les dice
  • Preguntar temprano vale más que resolver tarde. Nadie espera que sepan todo; esperan que avisen.
  • El código que van a tocar lo escribió otra persona, hace tiempo, con prisa. Leer código es la mitad del trabajo.
  • Un PR pequeño y claro se aprueba en una hora. Uno gigante se queda semanas.
  • La IA les va a dar velocidad. El criterio para saber si lo que produjo está bien, lo ponen ustedes.
Las empresas valoran menos cuánto React Native saben y más si entregan, preguntan, explican su código y cuidan main.

Bloque 2 · Primero, lo que no es

Tres cosas que van a escuchar y no son ciertas

Lo que React Native no es
  • Una página web metida en una app. Esas existen (se llaman híbridas) y se sienten lentas. React Native no es eso.
  • Un traductor a Kotlin o Swift. Su JavaScript sigue siendo JavaScript y viaja dentro de la app.
  • Lento por naturaleza. Esa fama viene de cómo funcionaba hace años. Ya cambió, y en un momento vemos por qué.
Lo que sí es
  • Una app de verdad, de las que se bajan de la tienda y se instalan.
  • Con un pequeño cerebro de JavaScript adentro que decide qué mostrar y qué hacer cuando el usuario toca algo.
  • Con un cable directo al teléfono para usar la cámara, el GPS, la base de datos o las notificaciones.
React Native es una app nativa que piensa en JavaScript.

Bloque 2 · Así se ve

Un componente, y lo que el teléfono crea con él

Saludo.tsx
// 1. Pedimos las piezas que vamos a usar
import { View, Text, Pressable } from 'react-native';

// 2. Una función que devuelve lo que se ve
export function Saludo() {
  return (
    // 3. View: una caja que agrupa cosas
    <View style={{ padding: 16 }}>
      {/* 4. Text: el único lugar donde va texto */}
      <Text>Hola, Retos</Text>
      {/* 5. Pressable: algo que se puede tocar */}
      <Pressable onPress={() => console.log('tocado')}>
        <Text>Tóqueme</Text>
      </Pressable>
    </View>
  );
}
Hola, Retos
Tóqueme
Lo que aparece

Una caja con un texto y un botón. Al tocarlo, se ejecuta la función que pusieron en onPress.

Lo que el teléfono crea

Android: la caja es un ViewGroup, el texto un TextView, lo tocable un botón nativo. iPhone: UIView y UILabel. Mismo archivo, sin cambiar una línea.

No es HTML

No hay div ni button: son las piezas del teléfono con un nombre en común. Pronto lo leemos línea por línea.

Bloque 2 · Dentro de la app

Primero: ¿qué es un hilo?

Un trabajador

Un hilo es un trabajador dentro de la app. Toma tareas de una fila y las hace una por una, en orden. No puede hacer dos a la vez.

El principal

Cada app tiene uno principal: dibuja la pantalla, recibe los toques y corre su código. Si está ocupado, la pantalla no se mueve.

Los de fondo

Para lo que tarda (internet, disco, cámara) la app pide trabajadores extra. Hacen la tarea aparte y avisan cuando terminan.

Regla de oro del móvil: el hilo principal nunca se ocupa en algo largo. Si lo hace, la app se congela y el usuario lo nota en medio segundo.

React Native, por dentro, reparte el principal en dos (uno para su código y otro para dibujar). La regla es la misma: lo pesado, afuera.

Bloque 2 · Historia

El bridge: cómo se hablaban antes

Su JavaScript✉ ✉ ✉ ✉ ✉mensajes en fila, uno tras otroEl teléfono (Kotlin / Swift)
Qué era

Un puente entre dos mundos que no hablan el mismo idioma. Para pedirle algo al teléfono ("dibuja esto", "dame la ubicación"), su JavaScript escribía un mensaje de texto, lo ponía en una fila y el teléfono lo leía cuando podía. La respuesta volvía por la misma fila.

Por qué se notaba

Cada toque, cada scroll, cada "¿cuánto mide esta vista?" era un mensaje más. Con pocos no pasa nada. Con una lista larga o una animación, la fila se llenaba y la app iba un paso atrás del dedo.

Con el bridge se hicieron Instagram, Discord y miles de apps durante casi diez años. Funcionaba, pero era la parte más lenta de todo el sistema.
Bloque 2 · Historia

JSI: la puerta directa de ahora

Su JavaScriptse hablan de frente, al instanteEl teléfono (Kotlin / Swift)
Qué es

JavaScript Interface. Una capa delgada (escrita en C++) que deja que su JavaScript tenga en la mano las piezas del teléfono y las llame directo, como si fueran funciones suyas. Sin mensajes, sin fila, sin esperar turno.

Qué cambió para ustedes

Dibujar la pantalla y usar la cámara, el GPS o la base de datos ahora pasan por esta puerta. Desde React Native 0.82 (octubre de 2025) es la única que existe: el puente se quitó por completo.

Por eso van a leer que "React Native es lento": muchos artículos, y muchas respuestas de IA, siguen describiendo el puente. Cuando lo lean, miren la fecha.
Bloque 2 · Dos formas de empezar

React Native CLI y Expo

React Native CLI
  • El proyecto trae las carpetas android/ e ios/ a la vista. Ustedes compilan con Gradle y con Xcode.
  • Necesitan Android Studio en su máquina, y una Mac para iOS.
  • Cualquier librería nativa entra sin intermediarios. Control total, y también toda la responsabilidad.
  • Así están la mayoría de las apps con años en producción.
Expo
  • Un framework encima de React Native: router, librerías ya configuradas y herramientas de construcción.
  • Expo Go: prueban en su teléfono escaneando un QR, sin compilar nada. EAS compila en la nube, iOS incluido, sin Mac.
  • Las carpetas nativas se generan cuando hacen falta (prebuild). Mucha magia útil.
  • Es lo que la documentación oficial recomienda para un proyecto nuevo.
El código de React Native es el mismo en los dos. Lo que cambia es cuánto de lo nativo ven y manejan ustedes.
Bloque 2 · Nuestra decisión

En este módulo usamos React Native CLI

Por qué
  • Van a ver Android e iOS por dentro: AndroidManifest.xml, Gradle, Info.plist, el keystore. Lo necesitan para permisos y para publicar, y es lo que tocan en una app real.
  • Cuando una librería nativa falle, van a entender qué falló, en vez de ver un error que una herramienta escondió.
  • Lo que cuesta: una instalación más pesada y una primera compilación lenta. Por eso va a haber una guía paso a paso.
Y Expo, con honestidad
  • Es excelente y seguramente lo usen en algún trabajo. No lo evitamos por malo; lo dejamos para después por pedagogía.
  • Cuando entiendan lo que Expo hace por ustedes, lo aprenden en una tarde. Al revés no funciona igual.
  • Si la empresa de la práctica usa Expo, van a estar cómodos: los componentes, los hooks y la navegación son los mismos.
Aprender con CLI es aprender a manejar con caja mecánica: después, la automática se entiende sola.
