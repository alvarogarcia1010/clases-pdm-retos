Bloque 1 · Sistemas operativos

Dos sistemas, dos filosofías

Android (Google)
  • Domina el mercado mundial: alrededor de 7 de cada 10 teléfonos. En El Salvador, la gran mayoría.
  • Basado en Linux y de código abierto (AOSP). Cada fabricante le pone su capa: Samsung, Xiaomi, Motorola.
  • Miles de modelos, versiones y tamaños de pantalla. Más libertad, más fragmentación.
  • Publicar es barato y rápido: Google Play.
iOS (Apple)
  • Solo en dispositivos Apple. Hardware y software controlados por una sola empresa.
  • Pocos modelos, actualizaciones rápidas, rendimiento y seguridad consistentes.
  • Reglas más estrictas para desarrolladores y una revisión más exigente en la App Store.
  • Para compilar se necesita una Mac, sin excepción.
Para ustedes esto significa algo muy práctico: su app tiene que correr bien en Android de gama media, porque ahí están sus usuarios.

Bloque 2 · Las opciones

Cuatro formas de hacer una app en 2026

Nativo

Kotlin en Android, Swift en iOS.

Dos bases de código, dos equipos. La UI la dibuja el sistema y cada novedad de la plataforma llega el día uno.

Para: bancos grandes, cámaras, juegos.

Flutter

Dart. Lo impulsa Google.

Trae su propio motor gráfico y dibuja cada pixel: la UI es idéntica en Android e iOS porque no usa los componentes del sistema.

Para: interfaces muy propias; también web y escritorio.

React Native

JavaScript / TypeScript con React. Lo impulsa Meta.

Un solo código, pero los componentes son los nativos reales: un <View> es un View de Android o un UIView de iOS.

Para: equipos que vienen de web, apps de negocio.

Kotlin Multiplatform

Kotlin. Lo impulsan JetBrains y Google.

Se comparte la lógica (datos, red, reglas); la UI puede ser nativa en cada plataforma o compartida con Compose Multiplatform.

Para: equipos Android que quieren llegar a iOS.

Las cuatro dan apps nativas que se instalan desde la tienda. Lo que cambia es quién escribe la UI, quién la dibuja y qué equipo hace falta.

Bloque 2 · La diferencia que importa

¿Quién dibuja la pantalla?

Usa los componentes del sistema
NativoReact NativeKMP con UI nativa
  • Un botón es un botón de Android o de iOS: hereda el look, la accesibilidad y los cambios de cada versión del sistema.
  • Se ve ligeramente distinto en cada plataforma, y eso es lo que el usuario espera.
  • Lo que paga: depende de que el sistema tenga el componente, o de un módulo nativo.
Dibuja sus propios pixeles
FlutterCompose Multiplatform
  • Un botón es un dibujo de un botón, hecho por el motor del framework. Idéntico en todas partes.
  • Control total: animaciones y diseños que el sistema no ofrece se hacen sin pedir permiso.
  • Lo que paga: imitar el comportamiento del sistema (teclado, gestos, accesibilidad) y un binario más pesado.
Un botón de React Native es un botón de Android. Un botón de Flutter es un dibujo de un botón de Android. Los dos funcionan; cambia quién manda.

Bloque 2 · Puesta en común

Lo que probablemente salió

Logística

GPS continuo, cámara y batería en "cualquier modelo" empujan a nativo, o a React Native o Flutter con módulos nativos bien hechos. Si el equipo ya es Android, KMP es una salida elegante. La batería es el argumento decisivo.

Coworking

Validar rápido, poco dinero, teléfono y computadora: web o PWA primero. Cuando el negocio lo justifique, React Native tiene una ventaja: el equipo y parte del código ya son React.

Fintech

NFC, seguridad y la mejor experiencia posible, con presupuesto: nativo, o KMP compartiendo la lógica con UI nativa. La velocidad se compra con equipo, no con atajos.

Fíjense en lo que acaban de hacer: no eligieron por moda, eligieron por el problema. Ahora veamos qué hay dentro de la opción que elegimos nosotros.

Bloque 3 · Primero, lo que no es

Tres mitos que van a escuchar

Lo que React Native no es
  • No es una página web dentro de una app. Eso es una app híbrida (Ionic, Cordova): un WebView mostrando HTML.
  • No traduce su código a Kotlin o Swift. Su JavaScript sigue siendo JavaScript y se ejecuta dentro de la app.
  • No es "lento por definición". Esa fama viene de una arquitectura que ya no existe. Lo vemos en dos slides.
Lo que sí es
  • Una app nativa de verdad, compilada con Gradle o Xcode, instalada desde la tienda.
  • Con un motor de JavaScript adentro que decide qué vistas nativas mostrar y qué hacer cuando el usuario toca algo.
  • Con un puente directo al código nativo para todo lo que el teléfono sabe hacer: cámara, GPS, base de datos, notificaciones.
React Native es una app nativa cuya lógica y cuyo árbol de interfaz los decide JavaScript.
Bloque 3 · El recorrido

Qué pasa cuando corre su app

1 · Metro
Empaqueta

Une sus archivos TSX en un solo bundle de JavaScript. En desarrollo lo sirve por red: por eso un cambio se ve al instante (Fast Refresh).

2 · Hermes
Ejecuta

El motor de JavaScript de Meta, hecho para móvil. Precompila a bytecode para que la app abra rápido y use poca memoria.

3 · React
Decide

Compara el árbol de componentes antes y después de cada cambio y calcula lo mínimo que hay que tocar en pantalla.

4 · Fabric
Renderiza

Crea o actualiza las vistas nativas reales. <View> es un UIView o un android.view.View; <Text> es un UILabel o un TextView.

5 · TurboModules
Conectan

Cámara, GPS, SQLite: código Kotlin, Swift o C++ expuesto a JavaScript a través de JSI, sin serializar JSON ni esperar.

Su código decide qué; el sistema operativo sigue dibujando cómo. Por eso la app se siente nativa: lo es.
Bloque 3 · Así se ve

Un componente, y lo que crea en el teléfono

import { View, Text, Pressable } from 'react-native';

export function Saludo() {
  return (
    <View style={{ padding: 16 }}>
      <Text>Hola, Retos</Text>
      <Pressable onPress={() => console.log('tocado')}>
        <Text>Tóqueme</Text>
      </Pressable>
    </View>
  );
}
En Android

View → ViewGroup · Text → TextView · el toque llega como un evento nativo y termina ejecutando su función onPress en JavaScript.

En iOS

View → UIView · Text → UILabel · el mismo archivo, sin cambiar una línea.

No se preocupen por la sintaxis

El jueves la vamos a leer línea por línea. Hoy solo importa ver que esto no es HTML: no hay div, no hay button.

Bloque 3 · Dentro de la app

Tres hilos que conviene conocer desde hoy

Hilo de JavaScript

Donde corre su código: la lógica, los estados, las decisiones de React. Uno solo. Si lo bloquean con un cálculo pesado, la app "no responde" aunque siga viva.

Hilo principal (UI)

El del sistema operativo: dibuja las vistas y recibe los toques. Fabric lo usa para crear y actualizar la pantalla.

Hilos nativos de fondo

Red, disco, base de datos, cámara. Los módulos nativos trabajan ahí y avisan cuando terminan. Por eso casi todo en móvil es asíncrono.

Guarden esta imagen: en enero, cuando hablemos de asincronía y de estados de carga, todo se explica con estos tres hilos.
Bloque 3 · Antes y ahora

Del bridge a la Nueva Arquitectura

Antes: el bridge (2015 a 2024)
  • JavaScript y el código nativo se hablaban por mensajes JSON asíncronos, en lotes.
  • Cada toque, cada scroll, cada medida de una vista cruzaba ese puente. En listas largas y animaciones se notaba.
  • De aquí viene la fama de "React Native es lento".
Ahora: JSI, Fabric y TurboModules
  • JSI: JavaScript llama a C++ directo, de forma síncrona, sin JSON.
  • Fabric renderiza en varios hilos y puede medir y dibujar sin esperar al siguiente lote.
  • TurboModules se cargan solo cuando se usan. Desde React Native 0.82 (octubre de 2025) esta es la única arquitectura: el bridge ya no existe.
Cuando lean "React Native es lento" en un artículo o se lo diga una IA, miren la fecha de lo que está citando.
Bloque 3 · Dos formas de empezar

React Native CLI y Expo

React Native CLI
  • El proyecto trae las carpetas android/ e ios/ a la vista. Ustedes compilan con Gradle y con Xcode.
  • Necesitan Android Studio en su máquina, y una Mac para iOS.
  • Cualquier librería nativa entra sin intermediarios. Control total, y también toda la responsabilidad.
  • Así están la mayoría de las apps con años en producción.
Expo
  • Un framework encima de React Native: router, librerías ya configuradas y herramientas de construcción.
  • Expo Go: prueban en su teléfono escaneando un QR, sin compilar nada. EAS compila en la nube, iOS incluido, sin Mac.
  • Las carpetas nativas se generan cuando hacen falta (prebuild). Mucha magia útil.
  • Es lo que la documentación oficial recomienda para un proyecto nuevo.
El código de React Native es el mismo en los dos. Lo que cambia es cuánto de lo nativo ven y manejan ustedes.
Bloque 3 · Nuestra decisión

En este módulo usamos React Native CLI

Por qué
  • Van a ver Android e iOS por dentro: AndroidManifest.xml, Gradle, Info.plist, el keystore. Lo necesitan para permisos y para publicar, y es lo que tocan en una app real.
  • Cuando una librería nativa falle, van a entender qué falló, en vez de ver un error que una herramienta escondió.
  • Lo que cuesta: una instalación más pesada y una primera compilación lenta. Por eso hay una guía y la tarea de hoy.
Y Expo, con honestidad
  • Es excelente y seguramente lo usen en algún trabajo. No lo evitamos por malo; lo dejamos para después por pedagogía.
  • Cuando entiendan lo que Expo hace por ustedes, lo aprenden en una tarde. Al revés no funciona igual.
  • Si la empresa de la práctica usa Expo, van a estar cómodos: los componentes, los hooks y la navegación son los mismos.
Aprender con CLI es aprender a manejar con caja mecánica: después, la automática se entiende sola.

Bloque 4 · El flujo

El ciclo de vida de una funcionalidad

1. La tarea

Nace en un tablero (Jira, Trello) con un qué y un para qué. Ustedes estiman cuánto toma; al principio se van a equivocar, y es normal.

2. La rama y el PR

Nadie toca main directo. Se trabaja en una rama y se abre un pull request con descripción clara y capturas.

3. El code review

Otra persona lee su código antes de que entre y pide cambios. No es personal: es la herramienta de calidad más barata que existe.

4. QA

Alguien intenta romper lo que hicieron: teléfono viejo, sin internet, girando la pantalla. Si no lo rompen ellos, lo rompe el usuario.

5. El release

Build firmado, versión numerada, notas de versión, lanzamiento por fases. Después, monitoreo de errores en producción.

6. El mantenimiento

La mayor parte de la vida de una app no es construirla: es mantenerla. Por eso importa escribir código que otro pueda leer.

El café de hace un momento es la tarea del punto 1: nunca llega completa. Preguntar lo que falta antes de programar es parte del trabajo.
Bloque 4 · La práctica

Lo que les van a pedir, y lo que nadie les dice

Lo que dice el papel
  • Integrarse a un equipo con una app ya en producción.
  • Implementar componentes de UI y consumir APIs internas.
  • Participar en code reviews: recibir y dar retroalimentación.
  • Usar Git y un tablero de tareas como parte del flujo diario.
  • Ayudar a encontrar y corregir errores en producción.
Lo que nadie les dice
  • Preguntar temprano vale más que resolver tarde. Nadie espera que sepan todo; esperan que avisen.
  • El código que van a tocar lo escribió otra persona, hace tiempo, con prisa. Leer código es la mitad del trabajo.
  • Un PR pequeño y claro se aprueba en una hora. Uno gigante se queda semanas.
  • La IA les va a dar velocidad. El criterio para saber si lo que produjo está bien, lo ponen ustedes.
Las empresas valoran menos cuánto React Native saben y más si entregan, preguntan, explican su código y cuidan main.
Resumen

Lo que vimos hoy

El mundo móvil

Android domina, iOS exige. Nativo, multiplataforma o web no se eligen por moda sino por el problema, el equipo y el presupuesto.

Cuál elegir

Nativo, Flutter, React Native y Kotlin Multiplatform: la diferencia de fondo es quién dibuja la pantalla y qué equipo hace falta. Ustedes ya decidieron con tres casos.

React Native por dentro

Metro, Hermes, React, Fabric, TurboModules. Vistas nativas de verdad, decididas desde JavaScript. CLI para aprender; Expo después.

Si se llevan una sola idea: React Native no es una web disfrazada. Es una app nativa que piensa en JavaScript.
